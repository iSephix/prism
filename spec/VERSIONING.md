# Versioning and compatibility

There are three independent version spaces:

| Value | Current | Meaning |
|---|---|---|
| Software package | 0.3.0 | API, tools and implementation release |
| Optical wire formats | 2 and 3 | Header, geometry, glyph meaning, placement, field arithmetic and typed content |
| Optical alphabet | 1 | The fixed ordered set of 19 printed glyphs |

Separate Community Draft 1 documents describe formats 2 and 3. The number 2 preserves codes already generated by the original Prism experiment; the standalone package started at 0.1.0.

Published format-2/alphabet-1 symbol meanings and algorithms are frozen. Editorial clarification can increment a document revision without changing the wire version. Any incompatible encoding change requires a new wire version; an incompatible glyph change also requires a new alphabet identifier. Decoder optimizations that read existing codes do not need a wire-version change.

For software 0.x, a patch release preserves the public API and existing wire support. An API-breaking change increments the minor version. Software 1.0 will require a reviewed specification, stable public API and published cross-device evidence; its release does not follow automatically from this draft.

Unknown wire versions, alphabet IDs, flag values and correction parameters are rejected. Reserved values are not extension points that individual implementations may allocate silently. A future proposal must document signaling, failure behavior, conformance vectors and migration from existing codes.

Decoders can expose independently identified experimental modes, but must not label them conformant format 2. Cryptographic algorithm or envelope-parameter changes require new signaling; the current encrypted flag fixes the suite described in FORMAT.md.

## Format 3 extension

[FORMAT3](FORMAT3.md) allocates a new wire version for larger payloads and typed content. It does not relax format-2 bounds or reinterpret old flags. The 0.3 encoder defaults to format 2 for small ordinary text/envelopes, and format 3 for larger or typed content. Decoders support both. Existing `vectors.json` remains unchanged; `vectors-v3.json` corroborates the new profile independently. The highest supported software wire version is 3, while each code reports its actual version.
